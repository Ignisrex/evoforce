# AGENTS.md

Working notes for AI coding assistants on the **evoforce** repo. Read alongside `SPEC.md` (source of truth for architecture and design rationale). This file is the *operating manual*: how things are laid out, where to put new code, and what not to break.

## Repo at a glance

```
evoforce/
├── core/        # Platform-independent game (Java, libGDX). Almost all code lives here.
├── lwjgl3/      # Desktop launcher (LWJGL3). Don't put gameplay logic here.
├── assets/      # PNGs, MP3s. assets.txt is regenerated by Gradle — don't edit by hand.
├── tools/       # Python (Pillow / pixellab) asset-generation scripts. Offline only.
├── SPEC.md      # Architecture & design spec. Update when behavior changes.
└── AGENTS.md    # This file.
```

All Java is under `core/src/main/java/com/silverignis/` and groups by concern:
`Main` → `screens/` → `state/` → `systems/` + `entities/` + `skills/` (+ `ui/`, `input/`, `components/`, `util/`).

## Where things live (cheat sheet)

| If you need to… | Look in… |
|---|---|
| Add or tune a skill | `skills/SkillLibrary.java` (data) + `skills/instances/*Instance.java` (behavior) |
| Add a new shape | `Skill.Shape` + new `*Instance` + add a case in `SkillFactory.create` |
| Add per-shape tuning data | new class implementing `skills.ShapeConfig` (see `ProjectileConfig`) |
| Add an action / rebind | `input/GameAction.java` (declare) + `KeyboardInputSource` + `GamepadInputSource` (map) |
| Change per-frame logic | `state/PlayState.update` (combat) or `state/SkillSelectState.update` (menu) |
| Change render order | `state/PlayState.renderWorld` (game world) or `screens/GameScreen.render` (HUD overlay) |
| Add a HUD element | new class in `ui/`, draw in `GameScreen.render`'s HUD pass |
| Add a panel type | `entities/Battlefield.PanelType` + matching `assets/panels/*.png` |
| Tweak game feel (timings) | `private static final float`s at the top of the relevant `*Instance.java` |

## Per-frame loop (don't reorder casually)

```
GameScreen.render(delta)
  ├─ InputManager.update()      # OR-fold sources, recompute edges
  ├─ currentState.input()       # dispatch GameActions
  ├─ currentState.update(dt)    # sim
  ├─ currentState.render(batch) # world
  └─ HUD pass                   # ChargeBarHud + SlotsHud always on top
```

`PlayState.update` order matters:
`player → enemy → charge → cooldowns → enemyAi → projectiles → combatSystem → CollisionResolver → vfx → cull dead`.
Skill instances thus see the same `originCol/originRow` they captured at construction *and* tick before collision resolution.

## Render layers (back → front, inside `PlayState.renderWorld`)

1. background image
2. battlefield panels
3. `combatSystem.renderUnder` — Zone effects (under entities for terrain feel)
4. player, enemy
5. basic-attack projectiles
6. `combatSystem.render` — beams, projectile sprites, auras
7. battle VFX (`ClashEffect`)
8. (HUD on top, drawn by `GameScreen`)

`ZoneInstance.isRenderUnder()` is the single hook that splits combat-system draws.

## Package dependency rules

```
screens, state    →    systems, entities, ui, skills, input
ui                →    skills (read-only)
skills            →    entities, components, systems
systems           →    entities
entities          →    components, util
components, util  →    (leaf)
```

**`components` must not depend on `skills`.** That's why `InputLock.lock(Object)` takes `Object` — the back-edge would create a cycle. Don't "fix" the type to `SkillInstance`.

## Conventions worth not breaking

- **`Skill` is immutable, pure data; `SkillInstance` owns behavior.** A `Skill` may spawn many simultaneous `SkillInstance`s. Don't put mutable runtime state on `Skill`.
- **One `SkillInstance` subclass per `Shape`.** The `SkillFactory` switch is meant to be exhaustive — keep it that way.
- **Phase enums + `phaseTime` accumulator** is the standard `SkillInstance` shape. Mirror the pattern when adding shapes.
- **Acquire `InputLock` only when you're driving the caster's body.** Strike does (whole life), Beam does (only during `CHARGE`/`FIRE`). Projectile/Aura/Zone do not.
- **Logical position snaps; visual position smooths.** `col/row` is authoritative; `PositionSmoother` is presentation-only. All writes go through `MovementSystem` — `tryGridStep` for input/AI (clamps to the entity's `GridBounds`), `forceGridTeleport` / `applyDisplacement` for skill-driven dashes/knockback (clamp only to the grid edge). Don't call `GridPosition.setTile` from outside the system.
- **Effects loop iterates `def.getEffects()` and only honors `Effect.Type.DAMAGE` today.** Other types (`APPLY_POISON`, `STUN`, …) are reserved — adding cases to existing instances is the right place when status effects land.
- **Spawn child instances via `ctx.combatSystem.spawn(...)`**, never by holding direct references between instances.
- **One-shot visuals → `ctx.vfx.add(new ClashEffect(...))`.** Persistent visuals → instance `render(batch, ctx)`. Don't draw outside the combat system's two passes if you want layering to behave.
- **Textures are owned by the closest scope and disposed there.** `SkillLibrary` disposes icons + VFX textures; `Battlefield` disposes panels; `PlayState` disposes its own. Never `new Texture(...)` in a per-frame path.

## Recipes

### Add a new skill (existing shape)
1. Append an entry to `assets/skills/skills.json`. Required fields: `id, displayName, description, icon, shape, element, cooldown, vfxTexture`. Optional: `effects` (array of `{type, value?, duration?, chance?}`), `vfxAnimation` (`{spritesheet, frameWidth, frameHeight, frameDuration}`), `shapeConfig` (`{movementType: STRAIGHT|LOB, ...}`).
2. Drop the icon under `assets/skills/`, the VFX under `assets/effects/`. Re-run the game so `generateAssetList` picks them up.
3. Done — no Java changes needed if the shape already exists. `SkillLoader` constructs the `Skill` via `Skill.builder()` and adds it to the library.

### Add a new shape
1. Add the value to `Skill.Shape`.
2. Create `skills/instances/MyShapeInstance.java` extending `SkillInstance` with a `Phase` enum + `phaseTime`.
3. Add the case to `SkillFactory.create`.
4. (Optional) If it needs tuning, add a `MyShapeConfig implements ShapeConfig` and read it in the instance constructor (mirror `ProjectileConfig`).
5. (Optional) Override `isRenderUnder()`-style hooks if it needs special layering.

### Add a new input action
1. Add the enum value to `input/GameAction`.
2. Bind it in `KeyboardInputSource.bindings`.
3. Wire the gamepad case in `GamepadInputSource.setButton` (and add a per-axis branch in `axisMoved` if it's a trigger / stick).
4. Read it from the relevant state via `screen.getInputManager().isAction*Pressed(GameAction.MY_ACTION)`.

### Add a panel type
1. Add it to `Battlefield.PanelType` with the texture path.
2. Drop the PNG at that path under `assets/panels/`.
3. Update `PanelGenerator` if you want it placed by default.
4. Behavior (slip/burn/heal/etc.) doesn't exist yet — see Known Gaps in `SPEC.md`.

## Build & run

Windows:
```
gradlew.bat lwjgl3:run        # run desktop
gradlew.bat lwjgl3:jar        # build runnable jar at lwjgl3/build/libs/evoforce-*.jar
gradlew.bat clean             # clean build outputs
```
POSIX equivalents are `./gradlew ...`. Java toolchain is **25**; libGDX **1.14.0**, LWJGL3 **3.4.1**.

`processResources` depends on `generateAssetList`, which writes `assets/assets.txt`. Don't edit that file by hand — it's regenerated.

## Common pitfalls

- **Don't hold a stale `Skill` reference in a slot expecting it to survive a `SkillLibrary.dispose()`.** Disposing the library disposes its textures; the `Skill` object itself is still in memory but its icon texture is gone.
- **Bounds-clamping is centralized in `MovementSystem.tryGridStep`**, which reads each entity's `GridBounds` (player = cols 0–3, enemy = 4–7). Don't re-derive the half-grid edge in new movement code; for skill-driven displacements that must cross it, use `forceGridTeleport` / `applyDisplacement`.
- **`SKILL_X/Y/B` is dual-purpose by state.** In `PlayState` it fires; in `SkillSelectState` it assigns. Keep both meanings consistent if you rebind.
- **Gamepad cancel is on `Back`, not `B`,** specifically so pressing `B` in the menu doesn't double-fire (assign-to-slot-B + cancel). Don't "simplify" by collapsing them.
- **`InputManager` and `GamepadInputSource` both keep current/previous maps.** That's intentional — see `SPEC.md` "Input pipeline". Removing either layer's edge detection will reintroduce double-fires.
- **There's no animation system yet.** If a feature feels like it wants animation states, propose the `AnimController` shape sketched in `SPEC.md` rather than bolting a one-off into `Player.render`.
- **Skill projectiles bypass `CollisionResolver`** today. They do their own per-tile overlap in `ProjectileInstance.checkHitStraight`. Don't add basic-attack-projectile-style logic to `ProjectileInstance` without first deciding whether to unify.

## When updating SPEC.md

Bump the spec when you change:
- Per-frame call order, render layer order, or package dependency rules.
- The `Skill` / `SkillInstance` / `ShapeConfig` contracts.
- The set of `GameAction`s, `Shape`s, `PanelType`s, `Effect.Type`s, or `Element`s.
- Resource ownership (who calls `dispose()`).

The "Known Gaps / Future Work" section in `SPEC.md` is the canonical TODO list — prune items as they're fixed.
